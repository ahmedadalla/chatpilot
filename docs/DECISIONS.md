## Q — Explicit product-owner requirements for this specification

The following requirements are taken from the reconciliation request. They are not
retrospectively attributed to an earlier product-owner session:

| ID | Requirement | Canonical interpretation |
|---|---|---|
| Q-REQ-1 | Hierarchy and isolation | Platform → Company → Branch → Users and Operations; company menus are shared across branches; tenant and branch data are isolated. |
| Q-REQ-2 | Role mandates | Super Admin manages the platform; Company Admin manages the company and branch lifecycle; Branch Manager manages the assigned branch operationally; Kitchen and Delivery have dedicated portals; all roles have real pages and backend actions when implemented. |
| Q-REQ-3 | Order terminality | `DELIVERED`, `CANCELLED`, and `FAILED_DELIVERY` are terminal. `FAILED_DELIVERY` is reachable only from `OUT_FOR_DELIVERY`, never from `DELIVERED`. |
| Q-REQ-4 | WhatsApp onboarding options | Three customer-selectable options in the connection wizard: (1) Regular WhatsApp QR/device pairing using the chosen library (Baileys/multi-device), available as a standard option in the wizard and not disabled by default, with explicit customer acknowledgement of unofficial status, session disconnects, and provider terms risks; (2) Official WhatsApp Business App Coexistence onboarding, where eligible, using official Meta infrastructure; (3) Direct official Meta WhatsApp Cloud API onboarding. Unofficial pairing is clearly distinguished from official Meta APIs and never misrepresented as Cloud API. All supported adapters implement the same secure company/branch routing and common conversation/order pipeline. |
| Q-REQ-5 | Hybrid branch-routing rule | Confirmed hybrid branch-routing rule: (1) A connection explicitly mapped to a branch routes directly to that branch; (2) A company with one active branch uses that branch automatically; (3) A company-level connection with multiple active branches requires customer branch selection before ordering; (4) The selected branch is persisted for the conversation (`Conversation.branchId`); (5) Branch resolution validates that the branch is active (`Branch.isActive = true`) and belongs to the company associated with the receiving WhatsApp connection (`Branch.companyId = Connection.companyId`); (6) No order is created while branch resolution is incomplete. |
| Q-REQ-6 | Target market defaults and localization | Egypt (`EG`) is the initial target market with international expansion readiness: (1) Default country is Egypt (`EG`, calling code `+20`), default currency is `EGP`, default timezone is `Africa/Cairo`, default locale is Arabic (`ar-EG`) with immediate switch to English (`en-US`), and full Arabic RTL support; (2) Phone validation/normalization uses `libphonenumber` supporting Egypt and international formats; (3) All country, currency, timezone, language, and phone defaults are strictly configurable per company; (4) EGP or Egypt-specific assumptions are never hardcoded into the DB schema or business logic; (5) Multi-currency separation is preserved in financial calculations and rollups; (6) Arabic product names, descriptions, customer messages, and AI responses are supported alongside English. |

No other historical “confirmed” decision is retained here without evidence. In
particular, prior claims that QR pairing or specific order rights were confirmed in
“Session 1” are removed rather than treated as product approval.

## D — Engineering defaults selected by the architect

| ID | Default | Rationale / boundary |
|---|---|---|
| D-1 | PostgreSQL 17 + Prisma 5+ | PG17 is the pinned target; UUIDv7 values are generated by the application because the baseline does not assume a built-in `uuidv7()` function. |
| D-2 | UUID columns use PostgreSQL `uuid` | Every PK/FK uses the same database type; UUIDv7 is an application-generation strategy, not a database function or authorization mechanism. |
| D-3 | `chatpilot_app` has no BYPASSRLS, is not a superuser, and does not own tables | RLS remains active for runtime access; migrations use a separate DSN/role. |
| D-4 | Transaction-local GUCs | Scope is set with typed, parameterized functions and `set_config(..., true)`; missing or empty context fails closed. |
| D-5 | Platform scope is unavailable to ordinary workers | Tenant workers use a DB-verified company/branch binding. Platform rollups consume approved aggregate sources; only the audited PlatformSupportService may establish platform scope. |
| D-6 | BFF single-origin browser path | API is not browser-reachable; secure HttpOnly SameSite=Lax cookies are paired with origin checks and CSRF protection on state-changing BFF routes. |
| D-7 | Cloud API webhook contract | Route by receiving business connection ID, verify the provider signature/challenge, use a five-minute freshness window, deduplicate by provider message ID, quarantine unknown connections, and acknowledge valid ingress within two seconds. |
| D-8 | Order transition idempotency & single winner | A uniqueness constraint including `actorUserId` does not collide across different actors. Single winner under concurrency is guaranteed by atomic conditional state update (`UPDATE "Order" SET status = :to WHERE id = :id AND status = :from`). Competing actors receive 409 Conflict when 0 rows match. `OrderTransitionToken` stores the claim for same-actor idempotent replay (returns cached result). Post-commit side effects use deterministic job IDs (`order:{orderId}:transition:{to}`). |
| D-9 | Order timeout | Default pending timeout is 15 minutes, configurable only within 5–120 minutes per branch; the sweeper performs a conditional first-writer-wins update. |
| D-10 | Date representation | `sequenceDay` is PostgreSQL `date` / Prisma `DateTime @db.Date`, computed in the branch IANA timezone. Timestamps remain `timestamptz` / `DateTime`. |
| D-11 | Multi-currency analytics | Store order currency and minor-unit-safe Decimal values; company/branch rollups remain currency-specific. Platform GMV is a per-currency breakdown plus an explicitly configured reporting-currency conversion, never an unlabelled sum of unlike currencies. |
| D-12 | BullMQ + Redis 7 | Scheduled and retryable workers use bounded retries, deterministic job IDs, and dead-letter alerting. |
| D-13 | Envelope encryption | AI credentials and WhatsApp credentials are encrypted through `SecretsService`; plaintext never enters DB rows, logs, responses, or prompts. |
| D-14 | Financial vs operational analytics separation | Operational analytics (order throughput, queue depth, prep/delivery durations) are accessible to operational roles for their branch. Financial analytics (GMV, revenue, average order value, pricing breakdown) are restricted to Super Admin, Company Admin, and explicitly authorized branch management; operational staff (Kitchen, Delivery, generic Staff) cannot access financial metrics. |
| D-15 | Cancellation usage accounting | A cancelled order retains its `order_created` usage event; no automatic credit is issued because the attempt consumed capacity. |
| D-16 | One role per user in v1 | Single `User.role` column; users hold exactly one role. Multi-role capability union semantics are deferred post-v1 via a separate role-assignment table. |
| D-17 | Multiple WhatsApp connections per company | A company may hold multiple connections across any supported adapter (Cloud API, Coexistence, QR). Each connection is uniquely owned by one company with unique provider-specific keys `(provider, business_connection_id)` and, when present, `(provider, phone_number)`, with explicit branch routing or hybrid resolution. |
| D-18 | Audited Company Admin timezone corrections | `COMPANY_ADMIN` may update a branch IANA timezone with mandatory audit logging. Historical order timestamps (`createdAt timestamptz`) and already allocated `sequenceDay` date values remain immutable; the corrected timezone applies only to future order sequences and reporting boundaries. |
| D-19 | Required TOTP MFA for Super Admins in v1 | Super Admin accounts must enroll in TOTP MFA; initial bootstrap/enrollment provides 10 single-use cryptographically secure recovery codes (hashed at rest). SMS and WebAuthn are deferred. |
| D-20 | Multi-currency platform analytics default without FX conversion | Platform analytics aggregate and display metrics broken down by currency. Automatic FX conversion to a unified reporting currency remains deferred until an explicit reporting currency, approved rate provider, and rate-timestamp policy are signed off. |
| D-21 | Dedicated WhatsApp worker with Baileys | Regular QR pairing uses the maintained `@whiskeysockets/baileys` library embedded in a dedicated, isolated worker container (`apps/whatsapp-worker`), keeping long-lived multi-device sockets isolated from the main NestJS API. Session credentials are envelope-encrypted into PostgreSQL via `SecretsService`. Time-boxed POC in Phase 6 validates QR generation/refresh, session persistence, reconnect on restart, disconnect detection, message/media dispatch, and dedup. Evolution API is retained as an evaluated fallback; WPPConnect/Chromium is excluded due to memory overhead (350–600MB/session). |
| D-22 | Configurable localization and phone normalization | Monorepo apps configure `libphonenumber` with default Egypt country code `+20` and locale `ar-EG`, while supporting international numbers. `next-intl` provides `ar` (default) and `en` catalogs with Arabic RTL-first CSS layouts. `CompanySettings` and `Branch` store configurable country, currency, timezone, and locale fields; database schema and core services avoid hardcoded values. |

## R — Security/compliance risks requiring explicit approval

| ID | Risk | Current mitigation | Approval required |
|---|---|---|---|
| R-1 | Regular WhatsApp QR/device pairing is an unofficial adapter that carries session disconnects and provider terms risk. | Enabled as a standard wizard option per Product Owner approval; isolated in `apps/whatsapp-worker`; cleanly decoupled behind `WhatsAppProvider`; explicit customer acknowledgement checkbox required before pairing; session credentials envelope-encrypted; automatic reconnect and rate-limit guardrails; no unsolicited/bulk messaging designs. | Confirmed and approved by Product Owner for v1. |
| R-2 | Platform-wide analytics can become a cross-tenant escape hatch. | No worker platform scope; aggregate-only source and dedicated audited service path. | Security review of P8 design. |
| R-3 | Webhook replay/forgery can create duplicate business effects. | Signature verification, five-minute freshness, unique dedup key, quarantine, idempotent order/transition writes. | Security test gate before P6. |
| R-4 | Incorrect RLS or pooled GUC handling can expose tenant data. | Forced RLS, separate roles, typed transaction-local setters, startup self-test, real-Postgres tests. | Security test gate before P1. |
| R-5 | Multi-currency GMV can be misleading if currencies are summed. | Per-currency rollups and explicit reporting conversion only. | Product approval of reporting currency/rates before P8. |

## Register maintenance rules

- A business rule is not labelled “confirmed” unless the product owner explicitly
  confirms it; an architect choice belongs in D, not Q.
- Any change to the order matrix, scope model, RLS coverage, webhook contract, or
  worker privilege model requires corresponding real-Postgres/integration tests.
- Decision IDs referenced by the other five documents must exist in this file.
